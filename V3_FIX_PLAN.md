## 1. Какой результат нужен

Программа выбирает несколько интересных сюжетных веток произвольного фильма и сокращает
каждую в понятную историю. У истории есть хук, причина развития событий и подготовленный
финал. Разговор, вопрос, ответ и реакция сохраняются настолько, насколько это нужно зрителю.
Не нужно искусственно разбивать каждую историю на четыре драматические роли или на множество
коротких реплик. Связная сцена может остаться одним длинным монтажным блоком.

Роли разделяются так:

- LLM решает, какую историю рассказывать, какие причины и реакции необходимы, что можно убрать.
- Код определяет существование фраз, реальные интервалы, длительность, покрытие событий,
  допустимость хронологии, формат данных и фактическое создание файлов.
- Проверяющий оценивает понимание и сохранение смысла. Он не заменяет расчёт времени.
- Интерфейс сообщает фактический результат: сколько историй принято, сколько видео создано,
  какие этапы завершились ошибкой и где лежат новые файлы.

Обещать определённое количество хороших историй из любого исходника нельзя. Если материала
или подтверждений не хватает, программа должна объяснить ограничение, сохранить годные
результаты и остановиться в пределах бюджета. Нельзя получать «успех» ослаблением проверок.

## 4. Этап A: результат прогона и понятные ошибки

### A1. Статистика очереди

В `pipelinemanager.h` добавить структуры `FileRunResult` и `QueueRunSummary`.
Хранить минимум:

- статус `completed`, `partial`, `failed` или `cancelled`;
- количество рассмотренных, принятых и отклонённых историй;
- количество историй с созданным видео и количество MP4-файлов;
- ожидаемые/созданные языковые версии;
- `outputs`: только пути файлов, созданных этим запуском;
- ошибки с кодом, этапом, ID ветки и путём диагностического файла.

История и языковая версия — разные счётчики. Три истории на RU и EN дают три истории
и шесть файлов, а не шесть историй. Отсутствие одной требуемой языковой версии отражается
в статусе, а не маскируется наличием другой.

В `addFilesToQueue()` обнулять статистику при начале новой очереди. Добавление файлов
во время обработки увеличивает общий счётчик, не сбрасывает накопленный результат.
В `finishCurrentFile()` финализировать каждый файл ровно один раз, затем обновлять итог.

В `processNext()` заменить безусловный текст итогом, например:

```text
Очередь завершена: 1 файл, успешно 0, с ошибками 1.
Новых историй: 0. Новых видеофайлов: 0. Рендер не запускался.
Причина: ни один монтаж не прошёл проверки.
Логи: ...
```

Сигнал `queueFinished` можно сохранить для разблокировки кнопки. Добавить отдельный
сигнал с `QueueRunSummary` для итогового блока интерфейса. В `mainwindow.cpp` показывать
статус и кнопки «Открыть новые клипы»/«Открыть логи»; первая доступна при непустом outputs.
Успех считать по фактически завершённым задачам рендера, не по ответу LLM и не по пустой очереди.

### A2. Парсер возвращает причину

Сейчас `LlmClient::parseStories()` возвращает `{}` при неверном ID или маркере.
Далее `validateStoriesV3()` сообщает о количестве историй и теряет настоящую причину.

В новом `storyprotocol.h/.cpp` добавить `ParseResult<T>` и `ValidationIssue`:

```cpp
struct ValidationIssue {
    QString code;          // INVALID_ENDPOINT, UNKNOWN_PHRASE, WRONG_TYPE...
    QString stage;
    QString branchId;      // новый контракт: "B1"; старый числовой ID адаптируется явно
    QString blockId;
    QString field;
    QJsonValue actual;
    QString expected;
    QString explanation;
    QJsonObject evidence;  // исходная фраза, время, допустимые соседние ID
};
```

Парсить сначала JSON-документ целиком. Разрешить снятие одной markdown-обёртки.
Для старых логов поддержать явно перечисленные формы: массив из одной истории и
новый объект `action=edit_story, story={...}`. Не выбирать первый встретившийся массив
из произвольного текста: это может оказаться массив segments вместо истории.

Проверять типы чисел и наличие полей до преобразования. Нельзя превращать отсутствующий
или строковый ID в ноль через `toInt()` без проверки. Несуществующая граница — ошибка
именно границы. Повреждённый блок нельзя молча выкинуть из готовой истории.

Пример результата для реального случая:

```json
{
  "code": "INVALID_ENDPOINT",
  "stage": "edit",
  "branch_id": "B12",
  "block_id": "B6",
  "field": "end_phrase",
  "actual": 1049,
  "expected": "ID речевой фразы",
  "explanation": "P1049 — музыкальный маркер, интервал 4794.22–4818.06",
  "evidence": {"previous_speech_phrase": 1048}
}
```

P1048 здесь подсказка для редактора, не разрешение автоматически удалить музыкальный
отрезок: он мог содержать важное действие. Для текстового этапа модель должна выбрать
допустимую речевую границу или обозначить потребность в визуальной проверке.

Старый `parseStories(..., phraseReferences=false)` для V2 не менять вместе с новым V3-контрактом.

**Тесты A:** ошибка P1049 не превращается в ошибку количества; несколько объектов
действительно дают WRONG_STORY_COUNT; неверный ID не удаляет один блок из истории;
успешный и неудачный файл в одной очереди дают разные итоги; повторный сигнал ошибки
не увеличивает счётчики дважды.

### B1. Хранилище этапов

Добавить `StoryRunStore` в `storyrunstore.h/.cpp`. Ответственность: версия протокола,
контроль зависимостей, атомарная запись, загрузка завершённых этапов. Не помещать эту
логику внутрь сетевого клиента. ASR-кэш и его текущие ключи сохранить.

Предлагаемая структура рядом с каталогом клипов:

```text
analysis/<analysis_key>/
  manifest.json
  index/window_01.json
  index/window_02.json
  event_map.json
  plans/<plan_key>.json
  branches/<branch_id>/context.json
  branches/<branch_id>/draft_v1.json
  branches/<branch_id>/timeline_v1.json
  branches/<branch_id>/viewer_v1.json
  branches/<branch_id>/fidelity_v1.json
  branches/<branch_id>/state.json
logs/<run_id>/...
```

Ключ окна: отпечаток исходника, содержимое транскрипта с ID/таймкодами/флагами, язык,
границы окна, модель и адрес провайдера без секрета, параметры генерации, версии
промпта/схемы/валидатора. Ключ плана дополнительно включает хэш карты, количество
историй и диапазон длительности. Ключ аудита включает хэш окончательного монтажа,
материал зрителя, версию проверяющего и модель.

Смена длительности должна пересчитать план и монтаж, но не ASR и не неизменённую карту.
Смена ревизора/транскрипта инвалидирует зависимую карту. Смена промпта зрителя инвалидирует
его оценки, но не извлечение аудио. Для ключей промптов/JSON использовать хэш содержимого,
а не время последнего копирования файла. Список зависимостей хранить читаемо в manifest.

Записывать через `QSaveFile`. Кэш считается пригодным только после проверки схемы,
хэшей и статуса `complete`. Для окон сохранять и принятые события, и оставшиеся цели
исправления. Повреждённый файл не приводит к использованию половины карты.

### B2. Режим запуска

В `appsettings.*` и `mainwindow.*` добавить явный выбор:

- «Продолжить анализ» — использовать совместимые завершённые этапы;
- «Пересобрать истории» — использовать карту, заново выполнить план/монтаж/проверки;

В начале писать, какие этапы взяты из кэша и какие вызовут LLM. Старые логи без manifest

### B3. Бюджет

Ввести `RequestBudget`, проверяемый **перед каждым фактическим POST**, включая сетевой
повтор. `LlmTransport` получает разрешение отправки от общего бюджета. Номер попытки
не должен обходить лимит логических запросов контроллера.

Предлагаемые начальные настройки, подлежащие оценке на тестах:

- максимум 80 API-запросов на файл;
- две доработки монтажа на ветку суммарно для технических и смысловых проблем;
- одно исправление формата ответа на ветку;
- одно дополнительное получение контекста на ветку;
- две резервные ветки сверх первоначальной цели.

На одну ветку закладывать до 11 логических обращений: три версии монтажа × (монтаж +
зритель + верность) = 9, плюс одно исправление формата и одно продолжение после запроса
контекста. Само чтение контекста с диска не является API-запросом. Сетевые повторы могут
увеличить количество фактических POST, но каждый учитывается в общем лимите 80.
Общий лимит может остановить работу раньше. Не обещать, что любой исходник даст минимум
историй в этом бюджете. Запросы планирования, исправления плана и проверки модели также
должны иметь явный бюджет; их нельзя считать бесплатными служебными операциями.

Сохранять `logical_request_id`, попытку, этап, ветку, время, usage, cached_tokens и
server_request_id, когда провайдер их прислал. Суммировать только известный usage.
Для оборванного запроса писать «расход неизвестен»; отсутствие ответа не означает нулевой расход.
Цены и списания не вычислять по выдуманному курсу или названию модели.

После исчерпания бюджета сохранить состояние. Возобновление запроса с неизвестным
результатом требует явного действия пользователя; не делать автоматический POST при
открытии программы. Сохранять уже реализованную защиту от повторов после тайм-аута.

**Тесты B:** второй запуск не вызывает ASR и индексатор при совпавших ключах; изменение
диапазона длины не сбрасывает карту; изменение транскрипта сбрасывает карту; повреждённый
кэш отклоняется; аудит не переиспользуется после изменения монтажа; API-повторы учитываются
в бюджете; unknown outcome не возобновляется сам.

## 6. Этап C: один расчёт монтажа для всех этапов

### C1. Компилятор временной шкалы

Добавить `StoryTimeline::compile()` в `storytimeline.h/.cpp`. Вход: черновик LLM,
индекс фраз/слов, карта событий, ограничения пользователя. Выход: `CompiledStory`
либо структурированные ошибки. В `CompiledStory` хранить исходные и окончательные
интервалы, длительность, текст каждого блока, покрытые события, нормализации и хэш.

Порядок обработки:

1. Проверить типы и существование start_phrase/end_phrase; маркеры не разрешать
   как речевые границы текущего текстового режима.
2. Получить интервалы из исходника. Не принимать длительность и секунды, придуманные LLM.
3. Проверить порядок и повторы, отдельно учесть разрешённый cold_open.
4. Нормализовать только доказуемые погрешности границ; записать каждое изменение.
5. Рассчитать паддинги без выхода за исходник и захвата другого выбранного интервала.
6. Рассчитать точную финальную длительность и набор реально слышимых реплик/слов.
7. Вычислить покрытие обязательных событий и завершения.
8. Проверить ограничения на итоговых интервалах и создать хэш.

Проверка порядка на шаге 3 сначала классифицирует проблему: маленькое перекрытие
соседних фраз передаётся шагу 4, а не отклоняется раньше нормализации. После неё
проверка повторяется строго. Иначе исправление 40 мс останется недостижимым кодом.

Зритель, проверка верности, субтитры и рендер должны получать **один CompiledStory**.
Перенести V3-паддинг из `PipelineManager::onStoriesFound()` сюда: сейчас проверяется
одна версия, а перед рендером интервалы ещё изменяются. Перед рендером сверить хэш;
любое смысловое изменение материала аннулирует старые аудиты.

### C2. Перекрытия соседних фраз

Для случая P1142/P1143 из лога допустима операция union: объединить два соседних
в порядке показа блока в один непрерывный интервал, если выбранные фразы идут подряд
и перекрытие вызвано небольшой неточностью ASR. Это убирает повтор 40 мс и лишний стык.

Начальное значение `timestampOverlapToleranceMs=80` — технический параметр, а не
разрешение повторять слова. Проверять одновременно близость времени, порядок ID,
отсутствие пропущенных речевых фраз и отсутствие перестановки сюжета. Не обрезать речь
по произвольной середине перекрытия. Большие/неоднозначные перекрытия отправлять на
исправление границ. Не сортировать cold_open или остальные блоки за спиной модели.

После объединения заново вычислять длину, покрытие, номера блоков и текст зрителя.
Перекрывающиеся интервалы не должны дважды учитываться ни в длительности, ни в рендере.

### C3. Цитаты и события выводятся из выбранного материала

Для нового V3-черновика LLM выбирает ID интервалов; не заставлять её вручную переписывать
цитаты для каждого блока. Код извлекает дословные реплики и формирует proof-данные.
Старое поле quote читать для совместимости и диагностики, но не использовать как
единственный источник длительности или текста нового протокола.

`event_ids` считать по реальному присутствию доказательств событий в блоке.
Присланные моделью ID являются подсказками и проверяются. Нельзя заявить покрытие
события только по названию или краткому описанию блока.

Покрытие означает включение проверенного доказательства из карты, а не доказанность
любой интерпретации события. Учитывать флаги качества ASR и прежние проверки цитат;
не превращать сомнительную фразу в уверенный факт при переходе на новый протокол.

Разрешить блоки `context`/`reaction` без самостоятельного события в карте, если они
состоят из реального материала и объяснена их связь. Их нужность оценивает зритель.
Сейчас требование события в каждом блоке отбраковывает полезные связующие реплики.

`required_events` должны фактически присутствовать. `ending_event` должен находиться
в завершающем эпизоде; после него допустима подготовленная реакция. Не требовать, чтобы
последним звуком ролика была именно цитата-доказательство. Связь финальной реакции
подтверждается материалом и аудитом, а не одним полем reason.

### C4. Длительность и хук

Текущие пользовательские 60–190 секунд сохранить. Короткий профиль, например 30–90,
можно добавить как явный пресет, но не включать автоматически. Если сюжет естественно
заканчивается на 26-й секунде, предложить другой замысел или другой пресет; нельзя
дотягивать его пустыми паузами и случайными репликами.

Для слишком короткого черновика ошибка должна содержать actual_sec, min_sec, deficit_sec,
длины блоков и доступные соседние блоки. Для слишком длинного — excess_sec и необязательные
материалы. Редактор делает осмысленный выбор, код пересчитывает результат.

natural: интересное начало уже является завязкой. cold_open: первый фрагмент до 12 секунд,
затем не более одного возврата и дальнейший исходный порядок. Если модель назвала
31-секундное естественное начало cold_open, не обрезать его автоматически: запросить
исправление режима или настоящий короткий хук по исходнику.

**Тесты C:** перекрытие 40 мс корректно объединяется без потери слов; настоящее повторение
материала отклоняется; P1049 даёт конкретную ошибку; пропущенное обязательное событие не
маскируется меткой event_ids; блок реакции разрешён; рендер и аудит получают одинаковый
хэш; после паддинга сохраняются 60–190 секунд; холодное открытие не превращается в сортировку.

## 7. Этап D: сначала пригодная ветка, затем монтаж

### D1. Подготовить материал для выбора

В `storycontext.h/.cpp` добавить:

```cpp
QList<SourceUnit> buildSourceUnits(const QList<S3Phrase>& phrases);
BranchContext buildBranchContext(const BranchPlan& plan,
                                 const EventMap& events,
                                 const QList<SourceUnit>& units,
                                 const ContextLimits& limits);
```

`SourceUnit` — непрерывный участок исходника с ID, границами фраз, точной длительностью,
репликами, флагами качества и связанными событиями. Это кандидат монтажного блока,
а не доказательство самостоятельной сцены. Смена голоса не равна смене сцены.

На первом этапе формировать единицы по паузам и непрерывности речи; сохранять варианты
контекста до/после события и ссылки на соседние единицы. Не обрезать длинный разговор
по универсальному правилу «каждые N секунд». При достижении размера контекста делить
представление на части, сохраняя соседство и возможность запросить продолжение.

Для планировщика строить компактные карточки событий: ID, короткий наблюдаемый факт,
отдельно заявление/предположение, evidence ID, необходимые знания, доступный эпизод,
диапазон длительности материала. Не отправлять одинаковые развёрнутые объяснения
из всех 481 событий в каждый последующий запрос.

Компактная карточка — проекция существующих полей карты в коде. Не добавлять отдельный
платный этап «LLM сокращает карту». Существующие indexPrompt и проверку доказательств
сохранить; для первой итерации менять потребление карты, а не заново проектировать индексатор.

Разделение двух задач:

- Карта всего фильма позволяет найти длинную ветку, проходящую через разные сцены.
- Контекст конкретной ветки содержит её причинную цепочку и необходимые соседние реплики.

Нельзя ограничить поиск ближайшими 30 секундами и тем самым снова превратить V3
в поиск отдельных эффектных сцен.

### D2. Новый план ветки

В `StoryNarrative::planPrompt()` и `LlmClient::acceptStoryPlanV3()` перейти к версии
контракта 2. На вход дать цель количества, резерв и реальные границы длительности.
Для настройки 3–19 сначала обрабатывать три лучшие истории; число 19 является потолком,
а не обязанностью сразу оплачивать 19 монтажей. Две резервные идеи запускать только
при недостатке принятых основных. Точные числа показывать в начале прогона.

План содержит:

```json
{
  "protocol_version": 2,
  "action": "plan_stories",
  "primary": [{
    "branch_id": "B1",
    "title": "Название без знания конкретного фильма",
    "dramatic_question": "Чего герой пытается добиться?",
    "hook": {"event_id": "C2E3", "mode": "natural", "why_interesting": "..."},
    "chain": [
      {"event_id": "C2E3", "function": "goal", "depends_on": []},
      {"event_id": "C4E2", "function": "obstacle", "depends_on": ["C2E3"]},
      {"event_id": "C6E8", "function": "payoff", "depends_on": ["C4E2"]}
    ],
    "required_events": ["C2E3", "C4E2", "C6E8"],
    "optional_events": [],
    "ending_event": "C6E8",
    "ending_effect": "Что зритель поймёт или почувствует в конце",
    "source_unit_ids": ["U12", "U47", "U81"],
    "missing_evidence": []
  }],
  "reserve": []
}
```

Код проверяет ссылки, отсутствие циклов зависимостей, уникальность замыслов и
доступность подтверждённого финала. Формулировка goal, совпадающая после замены одного
слова, ещё не доказывает другую историю: дополнительно сравнивать обязательные события,
финал и фактическое перекрытие материала. Не запрещать общий короткий контекст разных
историй, если развитие и завершение отличаются.

Пример смысловой инструкции планировщику:

```text
Выбери три разные истории из предоставленной карты и до двух резервных.
У каждой сначала определи интересное завершение, затем необходимые причины.
Опиши цепочку: исходная ситуация → препятствие/изменение → решение → результат.
Начало должно сразу давать интересный вопрос или ситуацию.
Сохраняй только связи, подтверждённые материалом. Не используй память о фильме.
Не требуй развязки всего фильма: достаточно подготовленного локального результата.
Используй реальные единицы материала и диапазон 60–190 секунд.
Если ветка требует отсутствующего визуального факта, укажи missing_evidence.
```

Числа здесь иллюстрируют последний запуск. В рабочем промпте подставлять
`targetCount`, `reserveCount`, `minSec`, `maxSec` из настроек; не зашивать 3 и 60–190.
Точную схему ответа добавлять отдельно к смысловой инструкции. Схема и валидатор
должны описывать одинаковые обязательные поля и допустимые значения.

### D3. Проверить реализуемость до платного монтажа

Из source_unit_ids код строит предварительный временной план: покрытие событий,
длительность без двойного счёта, естественное начало и завершающий эпизод.
Не принимать оценку LLM «примерно 90 секунд» как измерение.

Если даже минимальные необходимые фрагменты превышают максимум, вернуть планировщику
ошибку PLAN_TOO_LONG с вкладом каждого события. Если материала достаточно лишь на 26
секунд, при минимуме 60 ветка получает PLAN_TOO_SHORT: подобрать другой связный замысел
или осмысленно расширить цепочку до монтажа. Не заполнять дефицит случайным контекстом.

План в этом месте проверяется на техническую выполнимость, не объявляется художественно
успешным. Смысловая оценка остаётся отдельной стадией.

Различать нижнюю и верхнюю границы. Сумма целых SourceUnit не является минимальной
длиной: внутри разговора могут быть допустимые сокращения. Для доказанного PLAN_TOO_LONG
нужна нижняя граница по непересекающимся обязательным доказательствам и защищённым
репликам. Если доказанной границы нет, помечать риск длины и передавать задачу редактору.
PLAN_TOO_SHORT относится к выбранному набору материала, а не ко всему фильму:
планировщик может расширить связную цепочку, затем код повторяет предварительный расчёт.

### D4. Контекст монтажёра

`buildBranchContext()` возвращает только:

- текущий замысел и его цепочку;
- необходимые события и доказательства;
- полные реплики выбранных единиц и соседей, нужных для вопросов, ответов и реакций;
- ID допустимых речевых границ, начало/конец и точную длительность единиц;
- ограничения и краткий список уже использованного материала.

Начальный предел — 40000 символов на контекст одной ветки. Это настраиваемый инженерный
лимит для эксперимента; нельзя молча обрезать текст на 40000-м символе. Если обязательный
контекст не помещается, получить более узкий план или запросить нужную часть отдельно.

Разрешить действие `get_context` с конкретными event_id/phrase_id и целью запроса.
Контроллер проверяет ID и лимит, возвращает материал из этого исходника. Зритель не получает
этот инструмент. Для монтажёра достаточно одного дополнительного запроса на ветку в
начальном бюджете; нехватка контекста должна быть видна как ограничение, не как выдуманный факт.

### D5. Контракт монтажёра

Сохранить массив segments в модели данных, но выдавать историю в одном явном объекте:

```json
{
  "protocol_version": 2,
  "action": "edit_story",
  "branch_id": "B1",
  "story": {
    "title": "...",
    "description": "...",
    "story_summary": "Короткая цепочка причин и результата",
    "caption": "...",
    "score": 80,
    "opening_mode": "natural",
    "hook_reason": "Что заинтересует в первых секундах",
    "segments": [
      {"block_id": "B1_1", "start_phrase": 120, "end_phrase": 128,
       "role": "development", "reason": "Вопрос и ответ объясняют решение героя"},
      {"block_id": "B1_2", "start_phrase": 403, "end_phrase": 411,
       "role": "payoff", "reason": "Показывает результат и реакцию"}
    ]
  }
}
```

Цитаты, секунды, длительность и покрытие событий добавляет компилятор. score остаётся
самооценкой и не заменяет проверки; существующий пользовательский порог не отключать
скрытно. Его дальнейшее использование как ранга обсуждать отдельно от обязательных проверок.

Инструкция монтажёру:

```text
Сократи заданную сюжетную ветку до понятной истории с хуком.
Выбирай интервалы из предоставленных фраз. Сохраняй целые вопросы, ответы и нужные реакции.
Предпочитай меньше естественных блоков, если это сохраняет причины и финал.
Не добавляй закадровые объяснения: зритель услышит только выбранный звук фильма.
Учитывай указанные длительности. Все обязательные события должны остаться в материале.
Финальный блок/эпизод должен давать подготовленный результат.
Если причинного звена нет в контексте, запроси его; не сочиняй связку в reason.
```

**Тесты D:** ветка может выбирать материал из разных частей фильма; в запросе нет полного
транскрипта и посторонних веток; ограничения длины проверяются до монтажа; резерв не
обрабатывается заранее; get_context не открывает чужой фильм; сокращённый контекст
не теряет обязательные события. Размер и качество сравнить на одинаковых реальных ветках.

## 8. Этап E: исправлять нужную проблему

### E1. Явные состояния ветки

В `llmclient.h` вместо разрозненных флагов для нового V3 добавить сериализуемое состояние:

```text
planned → context_ready → draft_received → compiled
        → viewer_passed → fidelity_passed → accepted → rendered
```

Ответвления: format_error, technical_error, semantic_repair, needs_visual_review,
budget_exhausted, rejected. В состоянии хранить версии черновика/шкалы, счётчики попыток,
последние ошибки и хэши проверенных материалов. Не сбрасывать общий бюджет ветки при
каждом переключении Viewer/Fidelity/Repair. Старый текст ошибки не является состоянием.

### E2. Разделить причины и маршруты

| Ситуация | Действие |
|---|---|
| JSON не соответствует контракту | Один запрос исправления конкретных полей; художественный монтаж не переписывать |
| Неверный ID, длительность, повтор, хронология | Компилятор возвращает факты и допустимые варианты; редактор исправляет интервалы |
| Однозначная техническая нормализация | Код делает её сам, записывает изменение и проверяет полученную шкалу |
| Потеря причины, ответа, реакции | Редактор получает ошибку, затронутый стык и доступный контекст; меняет материал |
| Невозможно понять ASR | Проверить локальный фрагмент имеющимися ASR/ревизором либо выбрать другое доказательство |
| Смысл зависит от отсутствующего изображения | needs_visual_review; не выдавать текстовую догадку за подтверждение |
| Исправление не меняет материал/ошибку | Завершить бесполезный цикл и перейти к резервной ветке |

Техническая ошибка SHORT_DURATION должна содержать числа и длины блоков. MISSING_EVENT —
ID события, его доказательство и места, где его можно включить. BROKEN_TRANSITION —
два соседних блока, недостающее знание и цитату, из-за которой возникает проблема.

Промпт редактора:

```text
Исправь перечисленные проблемы текущего монтажа.
Сначала обеспечь реальные границы, длительность и обязательные события.
Затем восстанови недостающую причину, ответ или реакцию из предоставленного исходника.
Не переписывай проверенные части без необходимости. Не меняй смысл реплик.
Объяснение в JSON не исправляет то, что зритель не услышит/не увидит.
Верни полный обновлённый edit_story; программа заново соберёт и проверит его.
```

Полный новый черновик здесь предпочтительнее произвольного JSON-patch: меньше риска
сломать порядок блоков или применить изменение к устаревшей версии. Добавить
base_draft_hash и отклонять ответ для другой версии. При неизменном timeline_hash
повторный смысловой аудит не отправлять как будто материал изменился.

### E3. Контракт проверяющего

В `storyprotocol.*` отделить разбор отчёта от решения о качестве. Версия 2:

```json
{
  "protocol_version": 2,
  "action": "audit_story",
  "understood_story": "Что зритель понял из выбранного материала",
  "verdict": "repair",
  "issues": [
    {"block_id": "B1_2", "kind": "missing_context", "severity": "blocking",
     "problem": "Герой передаёт предмет человеку, доверие к которому не показано",
     "evidence": "Конкретная реплика или переход из показанного материала"}
  ]
}
```

Разрешённые verdict: pass, repair, needs_visual, unjudgeable. pass допустим только
при отсутствии blocking-проблем и наличии строкового understood_story. Advisory-замечания
не обязаны блокировать ролик. Нарушенный контракт даёт protocol_error, не pass и не
автоматический художественный брак.

Нормализация ограничена обёрткой и однозначным совместимым представлением.
Не превращать understood_story=true в строку «история понятна». Не выкидывать issues,
чтобы добиться pass. Для старых логов pass/understood_story/структурированные issues
переводятся в новый тип только при полностью корректном старом контракте.

Форматный повтор для ответа ветки 8 должен говорить буквально:

```text
Поле understood_story имеет тип boolean, требуется строка с пересказом понимания.
Верни audit_story по указанной схеме. Не переписывай транскрипт.
Сохрани реальные замечания; не выдавай положительную оценку ради исправления формата.
```

### E4. Что именно проверять зрителю

`StoryNarrative::viewerMaterial()` получает окончательный CompiledStory и выдаёт
только фактически оставленный материал в порядке показа, номера блоков и время ролика.
Не передавать план, event_ids, желаемый смысл, reason, исключённые реплики, названия
сцен и старые оценки. Исправленный монтаж проверяется новым независимым диалогом.

Инструкция зрителю:

```text
Ты видишь только этот ролик. Перескажи, что понял, затем оцени причинные переходы.
Начало должно давать интересную ситуацию; финал должен быть подготовлен материалом.
Неизвестное имя само по себе не является проблемой. Не требуй биографии или развязки фильма.
Блокирующая проблема — отсутствие сведений, без которых непонятно действие или решение.
Метки S0/S1 — непроверенные кластеры голоса, а не гарантированная идентичность персонажа.
Не исправляй ошибки ASR по памяти о фильме. Если они мешают понять смысл, укажи конкретный участок.
Без изображений не делай вывод о показанном действии: используй needs_visual, если это существенно.
Верни только audit_story. Не редактируй и не переформатируй расшифровку.
```

Проверяющий верность получает этот же монтаж плюс исходные эпизоды с достаточным
контекстом и относящуюся к ветке карту. Его задача — обнаружить ложную причинность,
смену адресата, отрицания, перепутанные знания и выдачу плана героя за свершившийся факт.
Удаление повторов и несущественных деталей само по себе не является искажением.

Ограниченный исходный контекст должен включать места, от которых зависят утверждения;
при его нехватке вернуть unjudgeable/запрос контекста. Нельзя объявить верность доказанной
по слишком узкому набору удобных цитат.

### E5. Совместимость модели

Добавить кнопку «Проверить формат LLM»: до двух коротких синтетических запросов с
явным указанием, что это API-запросы. Один пример связный, второй содержит пропуск причины.
Проверяется роль и схема, не художественное качество модели на полном фильме.
Результат кэшировать по адресу, модели, режиму API и версии контрактов.

Если выбранный провайдер поддерживает JSON Schema/structured output, включать режим
через проверенную настройку возможностей. Не предполагать, что любой адрес с /v1
поддерживает все параметры OpenAI. При неподдерживаемом параметре не повторять большой
платный запрос вслепую. Контракт кода остаётся обязательным и без серверного schema-mode.

**Тесты E:** реальные ответы веток 6/8 диагностируются как ошибки контракта; pass с
блокирующей проблемой запрещён; строковые замечания не теряются при исправлении формата;
зрителю не утекает план; редактор действительно меняет timeline_hash; после изменения
проходят обе проверки; лимит доработок общий и конечный; неизвестное имя не считается
автоматически потерей смысла; отрицание и смена адресата сохраняются.

## 9. Этап F: полезный результат и понятные файлы

### F1. Частично успешный запуск

Добавить явную настройку «Сохранять прошедшие проверку истории, даже если их меньше
заданного минимума». Предлагаемый режим по умолчанию — включён, с заметным статусом partial.
Это изменение поведения должно быть отражено в интерфейсе и заметках к версии.

Изменить обе точки: `LlmClient::startNextStoryBranchV3()` и
`PipelineManager::onStoriesFound()`. Передавать структурированный результат отбора,
а не превращать всякий недобор в errorOccurred. При 2 принятых из требуемых 3:
попробовать ограниченный резерв, затем сохранить две с предупреждением. При 0 принятых
рендер не запускать, статус failed. Эта функция сама по себе не исправит текущие 0 из 12.

Непроверенные черновики можно хранить как JSON для диагностики. Их видео-предпросмотр —
только отдельный явный режим с отметкой «не прошёл проверку», не обычные готовые клипы.

### F2. Отдельные результаты каждого запуска

В `buildStoryRenderTasks()` формировать пути:

```text
<film>_clips/runs/<run_id>/ru/story_01.mp4
<film>_clips/runs/<run_id>/en/story_01.mp4
<film>_clips/runs/<run_id>/stories.json
<film>_clips/runs/<run_id>/result.json
```

Существующие ru/story_01.mp4 и en/story_01.mp4 старых запусков сохранить. Их не включать
в outputs нового запуска. В интерфейсе открывать каталог конкретного результата, а не
общий каталог, где лежат старые файлы. `latest_attempt.json` указывает на последний
запуск; отдельный `latest_outputs.json` — на последний запуск, создавший годные файлы.
При неудаче не менять дату старого ролика и не объявлять его новым.

В `ClipRenderer` рендерить во временный `story_01.part.mp4`, затем проверять код завершения,
существование/размер файла и длительность через ffprobe. Только после этого переименовывать
в финальный путь и добавлять его в outputs. Для ограничения длительности учитывать
точность контейнера/кадра, а не объявлять любое округление новым браком.

Метаданные сохранять отдельно для отобранного монтажа и реально созданных версий.
Ошибка EN после успешного RU даёт partial и сохраняет RU. Не уничтожать уже готовый файл
из-за ошибки следующей задачи. Глобальные проблемы вроде отсутствия места прекращают
дальнейший рендер с объяснением, а не запускают бесконечные попытки.

**Тесты F:** 2 из 3 становятся partial, не completed; 0 из 3 остаются failed; старый клип
не считается новым; сбой второго языка сохраняет первый; незавершённый .part.mp4 не
появляется в outputs; счётчики историй и языковых файлов различаются; итог соответствует
файлам на диске.

Никаких сетевых запросов, изменения оригинальных логов и подмены исходного транскрипта.

## 12. Проверка с LLM и критерии готовности

После локальных тестов использовать проверенную карту последнего запуска и сначала
одну ветку. Не повторять десять окон индексации ради изменения промпта редактора.
Для проверки контекста сравнить одинаковую ветку с полным и ограниченным материалом
в пределах заранее заданного бюджета. Оценить ответы и расход, не только число успешных JSON.

Для первой практической проверки выбрать ветку с преимущественно речевой причинностью.
Зафиксировать ID выбранной ветки как тестовую конфигурацию, а не зашивать её в алгоритм.
После успешной одной истории проверить три разные ветки. Затем минимум три разных
исходника: диалоговый фильм, комедийный эпизод и материал с заметной долей действия.
Один исходник оставить вне настройки промптов для проверки переносимости.

Для каждого полученного ролика человек оценивает:

- цепляет ли начало и понятно ли, за чем следить;
- можно ли объяснить последовательность причин и решений без знания фильма;
- подготовлен ли финал;
- заканчиваются ли реплики естественно, сохранены ли ответы и реакции;
- нет ли придуманного смысла из-за склейки;
- ощущаются ли стыки естественно при просмотре со звуком.

Для молчаливого действия отметить границы возможностей текстового этапа. Полноценная
проверка такого материала требует следующего визуального этапа: последовательностей
кадров выбранных блоков, проверенных событий visual/mixed и проверки стыков. Предыдущая
просьба остановить развитие визуального этапа не отменяется созданием этого плана.

Готовность исправлений подтверждена, когда:

1. Сообщения интерфейса и result.json совпадают с фактическими файлами.
2. Длительность, покрытие событий и границы вычисляются из одного окончательного монтажа.
3. Ошибки ID, формата и ASR-границ диагностируются отдельно от художественных проблем.
4. Повторный анализ использует совместимый кэш и соблюдает бюджет запросов.
5. На подходящем речевом материале получены несколько связных историй, просмотренных человеком.
6. Неподходящий/недостаточный материал приводит к понятному partial/failed, а не ложному completed.
7. Сохранены проверки V2, ASR-кэша, RU/EN и защиты от повторных платных генераций.

## 13. Как разбить реализацию на проверяемые коммиты

| Коммит | Содержание | Проверка перед следующим |
|---|---|---|
| 1 | Итоги очереди + точные ошибки парсинга | Прогон с 0 файлов отображается как failed; воспроизведён P1049 |
| 2 | Хранилище карты/планов и импорт старого анализа | Возобновление без лишнего ASR/LLM; инвалидация зависимостей |
| 3 | Бюджет и учёт запросов | Повторы и исправления не обходят общий лимит |
| 4 | Единая временная шкала | Перекрытия, паддинги, длительность, покрытие и хэш проверены локально |
| 5 | Единицы материала и контекст ветки | Контекст ограничен, обязательные причины сохранены |
| 6 | Планирование реализуемых основных/резервных веток | Непригодные по длине планы отбрасываются до дорогого монтажа |
| 7 | Контракты редактора/аудитов и цикл исправления | Схема не маскирует провал смысла; исправленный материал перепроверяется |
| 8 | Частичный рендер и отдельные результаты запусков | Успех подтверждён файлами; старые результаты не потеряны |
| 9 | Оценка одной, затем нескольких веток и разных фильмов | Зафиксированы видео, измерения расхода и человеческая оценка |

Каждый коммит должен оставлять приложение собираемым. Новые контракты сначала
подключать за версией V3 и совместимым адаптером, затем переводить контроллер.
Не отключать проверки, чтобы сделать промежуточный тест успешным. Тестовые примеры
из конкретного фильма остаются тестами; рабочие правила должны использовать только
предоставленный исходник, его ID, время и подтверждённые события.
